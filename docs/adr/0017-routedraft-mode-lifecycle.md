# RouteDraft has an explicit `unsaved | editing` mode lifecycle

The RouteDraft owns a `mode` discriminant: `{ kind: "unsaved" }` for fresh composition, or `{ kind: "editing", routeId, baseline }` when bound to a saved Route. The `baseline` snapshots the saved fields (name, activity, privacy, tags, waypoints) so dirty detection is a structured comparison against that baseline rather than a string-stringify on a partial copy held elsewhere. Save branches on the mode: unsaved opens the metadata modal and POSTs a new Route; editing PATCHes the bound Route. Activity is a property of the RouteDraft; the global activity setting is a default for new drafts only and is never overwritten by loading a Route. The mode and baseline are persisted alongside waypoints; on rehydration the routeId is re-validated and the draft falls back to `unsaved` if the bound Route no longer exists or the user is not authenticated. Save, Duplicate, Load, and Clear all flow through `RouteDraftEditor` (per ADR-0009); panels and the command palette never set this state directly.

## Considered options

- **Flat optional fields on `RouteDraft` (`loadedRouteId?`, `baselineName?`, `baselineWaypoints?`, ...)** rejected: each editable field becomes its own optional pair, dirty detection grows asymmetric (some fields have a baseline, others compare to global state), and "is this draft bound to a saved Route?" has no single source of truth.
- **Keep `loadedRoute` on `uiStore` as originally shipped** rejected: split state between `uiStore` and `routingStore` forced JSON.stringify-based dirty detection across stores, made every panel reach into UI state to coordinate domain mutations, and (with `loadedRoute` non-persisted but waypoints persisted) silently turned reloaded edits into forks.
- **Treat `editing` as a separate top-level store** rejected: it is conceptually a property of the draft, not a sibling of it. A discriminated union on the draft makes invalid states (editing with no routeId, unsaved with a baseline) unrepresentable.
