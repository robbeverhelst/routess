# Browser error reporting via Sentry SDK + GlitchTip backend

The web app reports browser errors, performance traces, and Web Vitals to a self-hosted GlitchTip instance using the official `@sentry/react` SDK. GlitchTip is Sentry-protocol-compatible, so the SDK is unmodified and switching to hosted Sentry later is a DSN swap, not a code change. The capture surface is "maximal-for-GlitchTip": errors, breadcrumbs, releases tied to `VITE_APP_VERSION`, source maps uploaded at build time, performance traces at 10% in production and 100% in staging, Web Vitals on every sampled transaction, and structured logs from the existing `Logger`. Session replay and profiling are intentionally **not** wired — they are not supported by GlitchTip and shipping the dormant `@sentry/replay` package would cost ~70KB on every page load to save 20 minutes of integration work the day we cut over to Sentry. The DSN and tunable knobs (`VITE_SENTRY_DSN`, `VITE_SENTRY_ENVIRONMENT`, `VITE_SENTRY_TRACES_SAMPLE_RATE`, `VITE_SENTRY_LOGS_ENABLED`, `VITE_SENTRY_DEBUG`) ride the existing `env-config.js` runtime-injection pattern alongside Mapbox, Google OAuth, Umami; init no-ops if the DSN is absent or still the unsubstituted placeholder, so `bun dev` and any consumer rebuilding the image without configuring GlitchTip get a silent passthrough. Source maps are generated for both prod and staging and uploaded inside the Docker build via a BuildKit `--mount=type=secret,id=sentry_token` mount that never enters image layers; the `.map` files are deleted from `dist/` before the final image layer, keeping the published image portable and free of source-map exposure. The existing `errorHandler` singleton is kept as the **UI toast + domain-categorisation** layer, not a capture layer: its `window.error` and `unhandledrejection` listeners are removed (Sentry's `GlobalHandlers` integration replaces them), the `setErrorReportingService` slot is deleted, and `errorHandler.handleError(...)` now calls `Sentry.captureException(err, { tags, extra, level })` so every existing `handleAPIError` / `handleMapError` / `handleRoutingError` call site automatically ships rich domain-tagged events to GlitchTip without touching consumers. Sentry's global handlers stay on as a backstop for truly uncaught errors; those arrive without domain tags, which is honest — we don't know what category they belong to. TanStack Router is wired via `tanstackRouterBrowserTracingIntegration()` for per-route transactions and loader-error capture. React Query is intentionally **not** globally wired because the api-client funnel through `handleAPIError` already covers every error that matters. PII is minimised: `sendDefaultPii: false`, no IP, no email, only `Sentry.setUser({ id, segment: role })`; `beforeBreadcrumb` strips `access_token`, `code`, `state`, `id_token`, `token` from fetch URLs; a small in-memory `beforeSend` rate limiter caps each unique message at 10 events per minute to defend against runaway loops since GlitchTip self-hosted has no ingest-side spike protection. Domain context (`route_draft` shape — counts and distances only, never coordinates; `map_view` state; `user_session`) is attached via `Sentry.setContext` from store subscribers, and a thin `breadcrumb()` helper in `lib/telemetry` wraps `Sentry.addBreadcrumb` so future tracker swaps touch one file. `apps/api` and `apps/docs` are out of scope for this round; GlitchTip can host their projects under the same org when they land.

## Considered options

- **Roll our own error logger** (window listeners → POST to a NestJS endpoint) rejected: reinvents grouping, deduplication, source-map symbolication, rate-limiting, breadcrumbs, releases, and PII scrubbing. We'd ship a worse version of Sentry, and pay maintenance cost forever. The cost-of-not-using-the-SDK is negative.

- **Wrap the SDK in our own facade** rejected: the SDK *is* the abstraction. GlitchTip and Sentry consume the same Sentry-protocol events, so the swap is a DSN change. Adding a wrapper buys nothing and forces every Sentry feature (custom integrations, framework helpers, replay APIs) to be re-exposed through the wrapper before it can be used. Future-proofing through indirection that nothing today benefits from.

- **Make `errorHandler` the single capture funnel and disable Sentry's `GlobalHandlers`** (option b in the design discussion) rejected: it requires us to *guess* a category for every error, including genuinely uncaught third-party throws (Mapbox internals, browser extensions). The handled-error path (`handleAPIError`, etc.) covers the surface where we have real domain knowledge; for everything else, "no tag" is more truthful than "category: unknown" and lets Sentry's default integrations do what they're designed for.

- **Delete `errorHandler` entirely and use Sentry directly** rejected: the existing layer carries real value beyond capture — toast UI orchestration via pub/sub, domain-aware category/severity classification (which become rich Sentry tags), and integration with `ErrorToast` and `ErrorBoundary`. Ripping it out would force every call site (`api.ts`, `MapCanvas.tsx`, the boundary, geolocation paths) to grow Sentry-specific wiring inline. Keeping the layer and pointing it at Sentry is strictly cheaper.

- **Pre-wire session replay behind an env flag** so flipping to Sentry is one variable rejected: replay is ~50–80KB gzipped. Shipping it dormant to every mobile route-planning session to save ~20 minutes of integration work on the cutover day trades real user TTI cost for hypothetical future convenience.

- **Build-time DSN baked into the bundle** rejected: forces a separate image per environment, breaks the same-image-deploys-anywhere pattern the rest of the app's config already follows (Mapbox, Google, Umami), and prevents DSN rotation without rebuild.

- **Hosted GlitchTip** (glitchtip.com) rejected for now: the "log as much as possible" goal is incompatible with a per-event quota; self-hosting on the existing cluster is event-unlimited and matches the data-residency posture of every other backend in the stack.

- **Include `apps/api` and `apps/docs` in the same change** rejected for scope: the web setup alone is a meaningful PR. API instrumentation needs its own design pass against the existing Prometheus + domain events + business analytics stack (ADR-0013, ADR-0014). Docs is mostly static MDX with low error surface; a 30-minute follow-up.
