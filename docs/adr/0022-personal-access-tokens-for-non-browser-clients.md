# Personal access tokens for non-browser clients

Non-browser clients (the `routess` CLI, AI agents, scripts) authenticate via Personal Access Tokens (PATs) rather than the cookie-based JWT session used by the web app. PATs are minted from the web app's Settings → API Tokens page (copy-paste flow, no device-code or local-callback flow in this iteration), carry one of two scopes (`read` or `write`), live in `Authorization: Bearer routess_pat_<43-char base62>`, and are stored hashed with argon2id reusing the password infrastructure from PR 148. A PAT is never valid against `/api/v1/admin/*` regardless of the owning User's role, and cannot delete the User account (`DELETE /v1/users/me` stays cookie-only).

This shape exists because issue #139 requires headless operation, and reusing the cookie JWT for non-browser clients couples session lifetime, CSRF posture, and revocation to a transport that scripts and agents do not have. Distinct PAT auth lets us version, scope, throttle, and revoke machine credentials independently of human sessions — and lets us bar PATs from admin operations without complicating the human-session middleware. The `routess_pat_` prefix exists for two reasons: leak detection via secret-scanning tooling (GitHub Secret Scanning Partner program, gitleaks, TruffleHog all match on prefixes), and a cheap server-side fast-reject in the auth middleware before any database lookup.

Scopes are deliberately coarse — `read` covers list/get/export and inspecting own profile; `write` extends to metadata-only mutations on Routes (rename, activity change, visibility change, delete) and on user preferences. Fine-grained per-resource scopes (`routes:read`, `places:read`, etc.) are deferred until concrete callers ask for combinations the two-bit model cannot express. PATs are subject to a per-`jti` rate limit reusing the existing `ThrottleStrict`/`ThrottleModerate` config on the same endpoints as cookie sessions; this isolates a runaway agent loop from the owning User's interactive session, which shares the User-level bucket. Route *creation* via PAT is out of scope for this iteration and lands with the planning surface in the follow-up ticket — until then, `POST /v1/routes` rejects PAT credentials with `FORBIDDEN`.

## Considered options

- **Reuse the cookie JWT as a Bearer token** — rejected: couples machine credentials to session lifetime, gives them admin reach by default, and leaks the same secret across browser tabs and CI environments.
- **Fine-grained scopes (`routes:read`, `routes:write`, `places:read`, `user:read`, `user:write`)** — rejected as premature; the two-scope model expresses every distinction current callers actually need, and the migration path to finer scopes (add new scope strings, treat older `read`/`write` as supersets) is cheap.
- **OAuth device-code flow or local-callback flow for CLI login** — deferred: both require web routes, polling endpoints, and a threat-modeling pass. Copy-paste from the Settings page is the strict subset of work needed regardless of which flow we eventually ship.
- **OS keychain storage in the CLI** — rejected: breaks in containers, in SSH sessions on locked keychains, and on Linux desktops without a keyring daemon. Plain `~/.config/routess/auth.json` at mode `0600` with `ROUTESS_TOKEN` env-var override matches the `gh`/`aws`/`kubectl`/`docker` convention.
