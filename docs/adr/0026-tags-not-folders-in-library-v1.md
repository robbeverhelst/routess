# Library organisation uses flat Tags, not folders or collections

The RouteLibrary v1 uses a single flat list of Tags (the **Tag** entry in CONTEXT.md) as the only organisational primitive beyond `RouteVisibility` and `RouteActivity`. There is no folder concept, no collection concept, and no nested grouping. A Tag is a lowercase alphanumeric-plus-hyphen string of 1 to 24 characters; a Route can carry up to 10 of them; the same Tag attached to two Routes is recognised as the same Tag for filter chips and aggregation but is not stored as a shared entity. The Route Library filters by activity, visibility, single-tag, and free-text search across name and description, and sorts by recent-update, created, name, distance, or elevation gain.

This shape exists because the actual organising work a user does at the scale of a personal RouteLibrary (target ceiling: a few hundred Routes) is *finding* a specific Route quickly, not modelling a hierarchy. Flat Tags solve that with one storage column, one filter chip row, and one DTO field; folders solve the same problem with a parent/child schema decision (one folder per Route or many?), a move-between-folders UI, a question about whether unfiled Routes count as a "default" folder, and a migration plan for the day a user wants to flip an existing folder into a tag or vice versa. None of that work pays for itself at the Route counts we observe. The 10-tag cap and 24-character length cap exist to keep the filter row a single horizontal scroll and to prevent the column from absorbing free-form notes; both numbers are conservative enough that we can raise them without changing the data model.

A future folder/collection feature is not foreclosed: it would attach a Collection entity to the User and reference Routes through a join table, leaving the existing `tags` column untouched. The decision recorded here is that v1 does not need it, and recording the decision matters because "Strava has Collections" is the obvious counter-pull and the team should not relitigate it without new evidence (a real user with hundreds of Routes hitting the filter limit, not a hypothetical one).

## Considered options

- **Folders only, no Tags.** Rejected: forces every Route into a single bucket and makes cross-cutting concepts ("hilly", "with friends", "race-prep") impossible without duplicating Routes. The flat-tag shape already covers the cross-cutting case, and the bucket case is well-covered by `RouteActivity` plus `RouteVisibility`.
- **Tags and folders together.** Rejected for v1: doubles the surface area of the library filter UI and forces a decision about whether folders are private or shareable. Defer until evidence demands it.
- **Strava-style "collections" (named ordered lists of Routes a User curates and can share).** Rejected for v1: a meaningfully different feature with its own sharing/visibility semantics. Worth doing later as its own ticket; not the right anchor for the v1 library cleanup.
- **No Tags at all, free-text search only.** Rejected: search misses the "give me anything I tagged `hilly`" use case, which is the one the user actually performs while planning a Sunday ride.
