# Confirmation header for destructive PAT operations

Destructive operations performed under a Personal Access Token must carry an explicit `X-Routess-Confirm: true` header. Without it the API returns `428 PRECONDITION_REQUIRED` with a `DomainError` body whose `details` describe what the operation would do, so the calling agent or CLI can surface a confirmation prompt to the user and retry with the header set. Cookie-authenticated requests (the web app) bypass the header check — destructive intent there is expressed through the UI itself. The gated operations are: `DELETE /v1/routes/:id`; `PATCH /v1/routes/:id` when the change sets `visibility` to `public`; and `DELETE /v1/auth/tokens/:id` when the token being revoked is the same `jti` making the request. `DELETE /v1/users/me` is not gated because PATs cannot reach it at all (see ADR-0022).

This shape exists because the skill file's "ask the user before destructive ops" recommendation is unenforceable text. An LLM agent in a tool-use loop can — and occasionally does — ignore instructions, retry past errors, or compose destructive sequences across turns. The header gate converts the recommendation into a protocol: the agent cannot bulk-delete or publish a User's Routes without a deliberate two-step interaction. Soft-delete (ADR-0012) gives us recovery if the gate is ever bypassed by a confused agent that does set the header reflexively, but the gate exists so that simple cases — a script in a loop, a tool-use turn fired without user confirmation — fail safely without depending on soft-delete cleanup later. The header is single-purpose and trivial to set, which matters because a heavier confirmation protocol (one-time confirm-tokens, two-round-trip intent endpoints) would add latency to every legitimate destructive op without meaningfully raising the bar against malicious or careless callers.

`visibility: public` is included alongside `DELETE` because making a Route public is the operation a confused agent is most likely to perform with surprising consequences — once shared, the URL can be archived externally, and reverting visibility does not unshare. Route renames, activity changes, and visibility changes to `private` or `unlisted` are not gated; they are reversible and uninteresting from an abuse perspective. The gated-op list is versioned with the API; adding to it is a non-breaking change (agents that always set the header are unaffected), removing from it is breaking and should be avoided.

## Considered options

- **Skill text only — trust the agent to confirm** — rejected: the recommendation is unenforceable, and the failure mode (a runaway agent bulk-deletes Routes or makes a User's library public) is exactly the kind of surprise we cannot rely on the User to detect quickly.
- **Two-step confirm-token flow** (`POST /v1/routes/:id/delete-intent` returning a one-time token, then `DELETE` with the token) — rejected for this iteration: adds a round-trip to every destructive op, requires server-side token storage with TTL pruning, and the bar it raises is not meaningfully higher than the single header against the threats we actually face (careless agents, not adversaries with stolen PATs).
- **Gate every PAT write, not just destructive ones** — rejected: route renames and activity edits are reversible and high-frequency; gating them turns common automation into a confirmation-pile and dilutes the signal of a real destructive prompt.
- **Apply the gate to cookie sessions too** — rejected: the web app expresses confirmation through its own UI (modal dialogs, explicit "Delete" buttons), and adding the header to every browser fetch is friction without security benefit.
