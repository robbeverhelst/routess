# Public route page URL shape and SEO

Public and unlisted Routes are addressable at `/r/{slug}-{id}` where `{slug}` is a 1 to 40 character kebab-cased ASCII transliteration of the Route's name, and `{id}` is the canonical Route ID. The trailing `-{id}` is the lookup key; the slug is decorative. When the persisted slug drifts from the canonical slug derived from the current name, the page replaces the URL with the canonical form via `history.replaceState` on render. The Route lookup goes through the existing `GET /v1/routes/:id`, which already returns 404 for `private` Routes to non-owners and 200 for `unlisted`/`public` to anyone (the URL is the capability per the RouteVisibility definition in CONTEXT.md).

SEO and link previews are rendered client-side: the `PublicRouteScreen` rewrites `<title>`, `<meta name="description">`, the Open Graph property set (`og:title`, `og:description`, `og:image`, `og:url`), the `twitter:card` hint, the canonical `<link>`, and the `<meta name="robots">` tag in a `useEffect` once the Route data has loaded. The `og:image` is a Mapbox Static preview URL (the same builder the share modal and library cards already use). For `unlisted` Routes the `robots` meta is forced to `noindex,nofollow`; for `private` Routes the underlying API call 404s and the page never renders the meta tags at all.

This is a deliberately small v1: client-side meta injection is sufficient for Twitter, Discord, Slack, and crawlers that execute JavaScript, but it is *not* sufficient for the Facebook scraper (no JS) and is weak for Google indexing. Hardening the SEO surface to a server-rendered shim (an HTML response written by the API or by a nginx `sub_filter` against the SPA shell, substituting the meta tags before the bot reads them) is the next step; the URL contract above is chosen so that step is purely additive — the server-rendered version uses the exact same Route ID lookup and the same canonical URL, it just executes earlier in the response.

## Considered options

- **Use `/r/{id}` without a slug** — rejected: sequential IDs leak the rough age of the platform, the URL gives the reader no hint of what they are clicking, and link previews on chat platforms truncate worse. Slug adds five lines (`toRouteSlug`, the redirect effect) for a real readability win.
- **Use a separate share-token instead of `{id}`** — rejected: the existing CONTEXT.md decision is that "the URL is the capability." Adding a separable token reintroduces a key-rotation lifecycle and conflicts with the model where flipping visibility takes immediate effect for everyone holding the URL.
- **Server-render the meta tags from the API now** — rejected for v1: the web app is currently nginx serving a static Vite build, and the API is a separate origin; threading bot detection or shared HTML rendering through this split is a meaningful infrastructure change. The client-side path ships in days, the SSR path takes weeks, and the URL contract picked here lets us replace the rendering path without rewriting the URL contract.
- **Use Next.js (move the public route page into apps/docs)** — rejected: introduces a third URL origin for an authenticated product surface, splits the share modal's link-construction across two apps, and pulls the Mapbox/route-data dependency tree into the docs app. Not worth it for one page.
