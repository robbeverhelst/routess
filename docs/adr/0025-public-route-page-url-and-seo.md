# Public route page URL shape and SEO

Public and unlisted Routes are addressable at `/r/{slug}-{id}` where `{slug}` is a 1 to 40 character kebab-cased ASCII transliteration of the Route's name, and `{id}` is the canonical Route ID. The trailing `-{id}` is the lookup key; the slug is decorative. When the persisted slug drifts from the canonical slug derived from the current name, the surface replaces the URL with the canonical form via `history.replaceState` on render. The Route lookup goes through the existing `GET /v1/routes/:id`, which already returns 404 for `private` Routes to non-owners and 200 for `unlisted`/`public` to anyone (the URL is the capability per the RouteVisibility definition in CONTEXT.md).

This URL contract is shared verbatim by two surfaces: the canonical public page served server-side by the landing app at `routess.com/r/{slug}-{id}` (and `routess.be/r/{slug}-{id}`), and the interactive in-app view served by the web SPA at the same path on the app origin. The slug logic (`toRouteSlug`, `buildRouteSlugId`, `parseRouteSlugId`) lives in `packages/core` so both surfaces build and parse the path identically. The visibility semantics apply on both: `unlisted` Routes are served with `noindex` (the SPA emits `robots=noindex,nofollow`; the landing page emits the same in its server-rendered head), and `private` Routes 404 to non-owners because the underlying API call does.

The SEO surface is the landing app's server-rendered page. It renders `<title>`, `<meta name="description">`, the Open Graph property set (`og:title`, `og:description`, `og:image`, `og:url`), the `twitter:card` hint, the canonical `<link>`, and `<meta name="robots">` into the initial HTML response, so non-JS scrapers (the Facebook scraper) and search crawlers read complete metadata without executing JavaScript. The `og:image` is a Mapbox Static preview URL (the same builder the share modal and library cards use).

The web SPA's `PublicRouteScreen` still injects the same meta tags client-side in a `useEffect`, but this is now an in-app nicety for users who land on the app origin (and for JS-executing chat unfurlers), not the SEO path. Share links built in the app point at `VITE_PUBLIC_ROUTE_BASE_URL` (the landing host) when set, falling back to the app origin until the landing viewer ships, so a shared link never 404s in the interim.

The landing viewer page is a follow-up PR. This ADR's contribution is the URL contract, the shared slug logic, and the API behaviour that both surfaces depend on.

## Considered options

- **Canonical page server-rendered by the landing app (chosen).** The landing app (`routess.com` / `routess.be`) already exists as a server-rendered marketing surface on the brand host, which is also where users expect a shared link to live. Rendering `/r/{slug}-{id}` there gives complete metadata in the initial HTML for every scraper, reuses the same Route ID lookup and canonical URL as the in-app view, and keeps the authenticated app origin out of the public-link path. Cost: one extra surface to keep in sync with the URL contract, which is why the slug logic moved to `packages/core`.
- **Client-side meta injection in the SPA as the SEO path.** Rejected as the primary path: it is sufficient for JS-executing unfurlers (Twitter, Discord, Slack) but not for the Facebook scraper and is weak for Google indexing. It is retained as an in-app nicety, not the canonical SEO surface.
- **Server-rendered shim against the SPA shell (nginx `sub_filter`) or API-rendered HTML.** Superseded by the landing-app approach. Both threaded bot detection or HTML rendering through the app/API split for one page; the landing app already does server rendering on the right host, so the shim buys nothing.
- **`/r/{id}` without a slug.** Rejected: sequential IDs leak the rough age of the platform, the URL gives the reader no hint of what they are clicking, and link previews on chat platforms truncate worse. The slug adds a few lines of shared code for a real readability win.
- **A separate share-token instead of `{id}`.** Rejected: the existing CONTEXT.md decision is that "the URL is the capability." A separable token reintroduces a key-rotation lifecycle and conflicts with the model where flipping visibility takes immediate effect for everyone holding the URL.
