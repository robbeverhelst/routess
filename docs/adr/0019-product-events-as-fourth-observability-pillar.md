# ProductEvents are a fourth observability pillar, sent to self-hosted Umami

Routess already distinguishes _route metrics_ (properties of a Route), _operational metrics_ (Prometheus time-series, bounded labels, no PII; see ADR-0014), and _business analytics_ (Postgres aggregate queries inside `apps/api/src/admin/`). Behavioural user-action events — `route_created`, `auth_wall_hit`, `gpx_imported`, `route_share_link_copied`, … — fit none of those: they are individual moments with per-event properties, not bounded-label time-series and not Postgres-derivable. They live in self-hosted Umami as **ProductEvents**, fired exclusively from the web client via a typed `trackEvent()` wrapper. The canonical taxonomy is `docs/agents/product-events.md`; the typed source of truth is `apps/web/src/lib/analytics/events.ts`.

ProductEvents are the raw stream that funnel and retention questions are derived from. Business analytics in the admin UI remain Postgres-authoritative — a broken Umami does not affect "signups by day" or "top creators," because those query `user` / `route` directly. Conversely, Umami answers "what % of users who hit the auth wall then started signup?", a question Postgres cannot answer without storing the event stream itself.

## Considered options

- **Push behavioural events into Prometheus** — rejected: per-event properties like `creation_source`, `failure_reason`, `entry_point` are exactly the unbounded-label cardinality ADR-0014 forbids. Funnel queries (sequence of events per visitor) are not a Prometheus capability.
- **Roll behavioural events into Postgres ourselves** — rejected: reimplements visitor sessioning, event storage with retention, funnel queries, and a dashboard UI. Umami already does this in ~one container.
- **PostHog / Amplitude / Mixpanel** — rejected for v1: better funnel and identify-and-merge support than Umami, but adds vendor lock-in or hosted-cloud spend at a stage where self-hosted Umami already covers signups, route lifecycle, and import/export questions. Revisit if cross-session identity stitching becomes a critical blocker.
- **API-side fires via a `ProductEventListener` on existing domain events** — rejected for v1: threading user-agent / IP / accept-language / anonymous session ID from request through domain event to Umami's HTTP collect endpoint is non-trivial, and the sub-second "tab closed between API 2xx and `track()` firing" loss is acceptable. The web client is the canonical firing seam. Revisit when the first webhook-driven event (likely `payment_completed` confirmation from Stripe in #135) lands.
